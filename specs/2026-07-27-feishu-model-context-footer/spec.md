# 飞书消息模型与上下文页脚

## 背景

当前 Walker 会把命令回复、模型列表、进度更新等内容推送到飞书。用户希望每次推送到飞书的消息底部都携带当前使用的模型和上下文大小，便于在群聊中快速判断本次响应的运行环境。

## 目标

- 所有由 Walker 主动推送或回复到飞书的文本、Markdown 和卡片消息，在消息底部展示运行信息页脚。
- 页脚至少包含当前会话模型和上下文大小两个字段。
- 页脚不可影响原有消息正文、命令行为、发送重试和分片逻辑。

## 非目标

- 不新增模型切换能力。
- 不改变飞书 API 鉴权、路由绑定或消息去重逻辑。
- 不引入持久化存储，仅使用当前会话或运行时可取得的数据。

## 推荐方案

在飞书发送封装层统一追加运行信息页脚。

数据流：

1. 业务逻辑继续调用现有飞书发送入口。
2. 发送封装层根据当前路由或会话上下文解析当前 session。
3. 从 session.model 或默认模型解析模型显示值。
4. 从可取得的运行时上下文/token 用量字段解析上下文大小；不可取得时显示 `unknown`。
5. 在消息底部追加统一页脚后发送到飞书。

权衡：

- 优点：改动集中，业务命令不需要逐个维护页脚，后续新增飞书消息默认受益。
- 缺点：发送封装层需要拿到当前会话上下文；没有上下文的系统消息只能展示默认模型或 `unknown`。

备选方案：逐个业务消息点手动追加页脚。

- 优点：每类消息可以定制展示。
- 缺点：遗漏风险高，新增消息需要重复改动，不符合“每次消息推送”的一致性要求。

备选方案：仅在 Agent 输出消息追加页脚。

- 优点：实现更小。
- 缺点：命令回复、错误提示、模型列表等飞书消息不覆盖，不满足“每次消息推送”。

## 需求

### REQ-001 统一页脚覆盖

所有 Walker 发送到飞书的文本、Markdown 和卡片消息，必须在底部包含运行信息页脚。页脚包含 `模型` 和 `上下文` 字段。

验收标准：

- `replyText`、`sendText`、`replyMarkdown`、`sendMarkdown`、卡片发送或更新路径生成的飞书内容包含页脚。
- 页脚只追加一次，重试发送或卡片更新不会重复叠加相同页脚。
- 原消息正文内容保持不变，仅在底部追加分隔后的运行信息。

### REQ-002 模型解析

页脚必须展示当前会话使用的模型。若 session.model 存在，使用该模型；否则使用配置默认模型；若仍不可取得，展示 `unknown`。

验收标准：

- 对象形式模型显示为 `provider/modelID`。
- 字符串形式模型按已有解析规则显示。
- 缺失模型不会阻塞消息发送。

### REQ-003 上下文大小解析

页脚必须展示当前可取得的上下文大小。若运行时提供 token/context 用量，展示该数值及单位；若当前数据源不可取得，展示 `unknown`。

验收标准：

- 存在上下文大小字段时，页脚展示稳定、可读的值。
- 缺失上下文大小字段时，页脚展示 `unknown`。
- 上下文大小解析失败不会阻塞消息发送。

### REQ-004 兼容性与可靠性

页脚追加不得破坏飞书消息格式、分片、重试、命令响应和卡片结构。

验收标准：

- 文本和 Markdown 分片仍遵守现有长度限制。
- 飞书 API 调用失败重试逻辑保持不变。
- 发送无会话上下文的消息仍可成功发送，并用 `unknown` 填充不可取得字段。

## 测试计划

- 补充或更新飞书 API/dispatcher 相关单元测试，覆盖文本、Markdown 和卡片消息页脚。
- 覆盖模型存在、模型缺失、上下文大小存在、上下文大小缺失四类场景。
- 运行相关测试文件，必要时运行全量测试。

## 自审

- 无占位符。
- 每个 `REQ-xxx` 均映射到 `requirements.json`。
- 已选定统一发送封装层追加页脚方案。
