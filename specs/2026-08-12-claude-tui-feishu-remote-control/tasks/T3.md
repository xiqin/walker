# Task 3: 飞书无窗口恢复集成闭环

## 描述

通过 dispatcher 的真实普通消息路径验证失效 Claude runtime 只恢复一次、先原子持久化 agentRef、不开新窗口，再向恢复后的唯一 PTY 投递 prompt。

## 依赖

- 前置 task：T2
- 外部依赖：现有 SessionService 持久化与飞书 API 测试替身

## 涉及文件

| 操作 | 文件路径 | 说明 |
|------|----------|------|
| 条件修改 | `src/dispatch/message-dispatcher.js` | 仅在集成测试暴露缺口时修正恢复、持久化与 prompt 顺序 |
| 修改 | `test/claude-tui-reconnect.integration.test.js` | 增加飞书恢复、并发、持久化失败和零窗口断言 |

## 复杂度

medium，原因：核心修复在 driver，但必须证明 dispatcher 的恢复分支、route 锁与关键字段持久化形成完整事务顺序。

## 实现步骤

- [ ] 构造已绑定精确 UUID、runtime 失效、terminal detached 的飞书会话 fixture。
- [ ] 断言普通消息调用一次 `resumeSession()`、零次窗口启动并向返回的 runtimeId prompt。
- [ ] 断言两个并发消息不会绕过 route/driver 恢复互斥产生两个 `--resume` runtime。
- [ ] 断言 agentRef 持久化成功发生在 prompt 前；持久化失败时 PTY 写入为零并返回明确错误卡片。
- [ ] 仅在现有 `_prepareClaudeAgentRef()` 顺序不满足测试时做最小修复。
- [ ] 验证 Walker 重启后的序列化 agentRef 可恢复而不会恢复窗口。
