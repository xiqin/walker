# 飞书消息页脚显示会话标题

## 目标

在已有模型、上下文页脚内显示消息所属会话的标题；正文和卡片共用同一渲染入口，不另发标题消息。

## 方案比较

1. 推荐：通过现有运行时元数据传递会话标题，在统一页脚生成器显示。无额外远端查询，覆盖文本、进度卡和问题卡；标题以 Walker 当前可用会话记录为准。
2. 每次发送前查询 OpenCode 标题：能获取远端重命名结果，但新增网络依赖，可能延迟推送，不符合本次最小范围。
3. 在每个发送入口拼接标题：单个入口简单，但容易漏掉卡片或造成重复页脚，不采用。

## 需求

- REQ-001：将消息所属会话的标题加入现有页脚，顺序为会话、模型、上下文；文本和已有运行时页脚的卡片保持一致。使用消息实际关联会话，不使用无关的路由焦点会话。标题缺失、无效或空白时不显示会话行，保留原有模型和上下文页脚。发送时使用现有会话数据，不为标题新增远端请求或持久化写入。
- REQ-002：兼容旧的模型和上下文页脚以及新增会话行的页脚。追加或更新页脚不重复保留旧页脚；回复去重忽略运行时页脚，不因标题变化重复推送正文。多行标题规范成单行并作为普通展示文本处理，不能注入额外页脚字段或卡片结构。

## 示例

```text
---
会话：飞书桥接修复
模型：seasun/gpt-6.1-sol
上下文：12000 tokens
```

## 不变量与非目标

- 不改变消息正文、路由、会话绑定、模型和上下文计算。
- 不修改 OpenCode 插件协议，不添加配置，不自动提交、推送或重启服务。
- 无会话信息的系统消息维持旧页脚。
- 不保证外部重命名在 Walker 尚未获知时立即反映；本次不增加标题同步机制。

## 验证

通过飞书 API 和调度器回归测试验证文本、卡片、标题缺失、多行标题、旧页脚替换、新页脚幂等、正文去重以及会话关联隔离。
